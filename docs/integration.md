# Integrating an application with OtterStax

How an application reads and writes the tables of its existing MySQL / MariaDB, PostgreSQL and
ClickHouse databases through OtterStax — one connection, one SQL dialect, JOINs across databases —
with its usual driver or ORM. This guide is the general approach, for any language and framework.
Framework code (Django, SQLAlchemy) and the runnable examples are in
[`examples/integration/CLAUDE.md`](../examples/integration/CLAUDE.md); the server's internals are in
`CLAUDE.md`.

> Status markers. **verified** — run against OtterStax by the examples of `examples/integration/`
> (2026-11-27, a Linux image of `main` at `961fa44`) or by the external compatibility board
> raft-board (2026-11-20, every major driver and ORM of Python, Go, Java, Node and Rust over both
> wires). **unverified** — follows from the server's documented behaviour, not run. Report a marker
> that is wrong.

## In short

1. Run OtterStax with your databases declared in its `config.yaml`; the application connects to
   OtterStax only.
2. Connect over the **PostgreSQL wire** with the PostgreSQL driver or ORM dialect you already use.
3. Name every table `alias.namespace.table`, and put `alias.namespace` into your ORM's schema slot.
4. **The backends own their schemas.** Write the models by hand, create tables with keys and
   generated ids on the backend itself, and run schema migrations against the backend, not
   OtterStax.
5. **Keep your framework's own tables** (migrations, sessions, users) in an ordinary database;
   OtterStax is a second connection for the models over your backends.
6. **One transaction writes to one backend.** Reads in it may span any backends.

What works through OtterStax: reads, JOINs across backends, inserts with ids generated by the
backend, updates, deletes, transactions and savepoints. What does not: anything that makes the ORM
read or change the database's structure (section 12).

## 1. What OtterStax is to your application

One SQL server in front of your databases. A statement may name tables of several of them;
OtterStax sends each backend the part it can answer (filters, aggregates, JOINs within it), and joins
the rest itself. To the application it is one PostgreSQL (or MySQL) server, with three-part table
names.

| Wire | Port | Use it for |
|------|------|------------|
| PostgreSQL | 8817 | applications, ORMs — the recommended wire |
| MySQL | 8816 | MySQL drivers and ORMs, with the limits of section 12 |
| Arrow Flight SQL | 8815 | analytics clients (ADBC) |
| Spark Connect | 15002 | PySpark |

## 3. Server and connections

The backends are declared in the server's `config.yaml`, read once at startup. Each one gets an
**alias**, the first part of its table names:

```yaml
service:
  engine: { data_dir: /otterstax/data }        # required
connections:
  postgresql:
    - { alias: pg,    host: pg-host,    port: "5432", username: app, password: secret,
        database: shop, schema: public, table: "" }
  mysql:
    - { alias: maria, host: maria-host, port: "3306", username: app, password: secret,
        database: billing, table: "" }
```

- There is no API to add a backend at runtime: edit the file and restart the server.
- OtterStax connects to each backend with the configured user: grant it what the application needs
  (reads, and writes where it writes).
- A server: build the image (`scripts/deps-image.sh release`, then `docker build -t otterstax:local .`)
  and run it with your config mounted:
  `docker run -p 8817:8817 -v $PWD/config.yaml:/otterstax/config.yaml:ro otterstax:local`.
  `examples/quick_start/` is a ready stack with four backends. The published image
  `ghcr.io/otterstax/otterstax:0.2.0` may not be public yet.
- There is no TLS on either wire: keep OtterStax on a private network or tunnel it.

## 4. Wire and driver

**Use the PostgreSQL wire**, whatever the backend behind it: every backend's tables are reachable
through it, and it returns generated ids for PostgreSQL and MariaDB backends (section 10). Use the
driver and ORM dialect you would use for PostgreSQL.

- A driver's connect-time queries (`version()`, type lookups, `SET` of client parameters) are
  answered; a lookup OtterStax lacks fails at connect. Known: SQLAlchemy's psycopg 3 dialect
  (`::regtype`); its psycopg2 dialect and Django's psycopg 3 backend connect. **verified**.
  The board in raft-board's README lists every driver and ORM it runs.
- The MySQL wire returns a generated id for a MySQL backend's table only (section 10).

## 5. The connection's database: the place

The database named when connecting is the session's **place**. It completes names of one or two
parts; three-part names do not need it:

| Wire | Write as database | A bare `items` means |
|------|-------------------|----------------------|
| PostgreSQL | `pg`, `pg.public`, `local`, `local.<schema>` | `pg.public.items`, … |
| MySQL | `pg.public`, `maria.billing`, `local` | the same |

- Anything else is refused at connect (`FATAL 3D000`).
- With every model carrying its full name, **`local` is a good default**: one connection reaches
  every backend. **verified**.
- Tools that list "the database's tables" see the place's tables only: none in `local`, a
  connection's own in `pg`. **verified**.

## 6. Table names and model mapping

Every table has a three-part name, **`alias.namespace.table`**:

| Backend | namespace is | Example |
|---------|--------------|---------|
| PostgreSQL | a schema of the configured `database:` | `pg.public.items` |
| MySQL / MariaDB / ClickHouse | a database of the server | `maria.billing.invoices` |
| OtterStax's own tables | a schema of `local` | `local.public.notes` |

Names written without quotes are lower case. Four-part names are refused.

An ORM has one "schema" slot in front of the table name. OtterStax reads a quoted name holding dots,
whose first segment is an alias or `local`, as the name it spells, so **the alias and the namespace
go into that slot together**: schema `"pg.public"`, table `items` → `"pg.public"."items"` =
`pg.public.items`. An ORM without a schema slot quotes each part in its table name
(`"pg"."public"."items"`). Both forms **verified** on PostgreSQL, MariaDB and ClickHouse tables; the
per-ORM settings are in `examples/integration/CLAUDE.md` and raft-board's README.

Relations between models of different backends work for the ORM's JOINs (OtterStax runs them);
nothing enforces them as foreign keys.

## 7. Schemas: the backends own them

OtterStax serves the backends' tables; it does not hold their definitions for an ORM to read or
change.

- **Write the models by hand.** Schema reflection and model generators read PostgreSQL catalog
  columns OtterStax does not have, and fail or answer wrongly (SQLAlchemy's `has_table` answers
  "no" for every table). **verified**.
- **Create tables on the backend itself** — with their keys, defaults and generated ids — with the
  backend's own tools or migration runner. Through OtterStax a `CREATE TABLE` of a backend table
  takes no keys, checks, defaults or `serial` (`NOT NULL` is fine), and any DDL of a backend table
  runs only in autocommit. **verified**.
- **A table created on a backend while OtterStax runs** is registered on its first use — if that use
  is outside a transaction. Inside one (an ORM's default: drivers open a transaction per statement)
  the first use fails with `relation "…" does not exist` and the next works. Touch a new table once in
  autocommit, or restart OtterStax. **verified**.
- `CREATE INDEX` on a backend table is refused.

## 8. The application's own state

Frameworks keep tables of their own: migration history, sessions, users, task queues. OtterStax
cannot hold them:

- its own tables (`local.*`) generate no ids — no identity column, `serial` or `nextval()` default —
  so a framework's auto-increment tables cannot be created there; **verified**;
- a framework's migration runner creates its history table with a key and runs inside a
  transaction, both refused on a backend (section 7).

So give the framework **two connections**: an ordinary database for its own tables and for the models
it manages, and OtterStax for the models over your backends, read and written through it. Route each
model to one of them; relations stay within one side, and an application joins across them in code.
**verified** (Django). OtterStax's `local` tables are fine for data the application keys itself.

## 9. Transactions and writes

- `BEGIN` / `COMMIT` / `ROLLBACK` and savepoints work, over reads of any backends. **verified**.
- **A transaction writes to one backend.** A write to a second backend in the same transaction fails
  it (`transaction already wrote to connection "pg"; writing to connection "maria" in the same
  transaction is not supported`). Write two backends in two transactions; mind frameworks that wrap a
  whole request in one. **verified**.
- An `UPDATE` / `DELETE` of a backend table runs as one statement of that backend: one that joins
  another backend is refused.
- ClickHouse has no transactions: write to it in autocommit.
- An open transaction holds one of the backend's `pool_size` connections (default 4) until it ends;
  more open transactions than that wait up to 60 s, then fail.
- A backend COMMIT is not two-phase with OtterStax's own: a crash between the two can leave the
  outcome in doubt.

## 10. Generated ids

- An INSERT sends only the columns given; the rest take the backend's DEFAULT / serial /
  AUTO_INCREMENT.
- PostgreSQL wire: the ORM gets the new id through `RETURNING`, from a PostgreSQL backend
  (**verified**) or a MariaDB 10.5+ one (raft-board).
- MySQL wire: `LAST_INSERT_ID()` is a MySQL backend's AUTO_INCREMENT only; a PostgreSQL table reached
  over the MySQL wire reports 0, and the ORM loses the new row (raft-board).
- ClickHouse and OtterStax's own tables generate no id.

## 11. Types and semantics

- Dates and timestamps come back as dates and timestamps, DECIMAL as decimal, a MySQL `TINYINT(1)` as
  boolean (any non-zero value true).
- `count(*)` is an unsigned 64-bit integer.
- Every backend session runs in UTC; a pushed-down `now()` or `::date` is evaluated in UTC.
- A pushed-down expression keeps its backend's semantics (division by zero: MySQL NULL, PostgreSQL an
  error, ClickHouse `inf`).
- Integer JOIN keys of different widths match: a backend `INT` joins a `BIGINT` (an ORM's default
  64-bit id) of another backend or of a local table. **verified**.

## 12. Limitations

| Feature | Status |
|---------|--------|
| Schema reflection, model generators, autogenerated migrations | fail, or answer wrongly |
| A framework's migration history / own tables on OtterStax | fail; use an ordinary database |
| `CREATE TABLE` with keys, defaults or `serial` on a backend | refused; create it on the backend |
| DDL on a backend inside a transaction | refused; use autocommit |
| Generated ids in OtterStax's own (`local`) tables | none |
| First use of a new backend table inside a transaction | fails once; touch it in autocommit |
| Writes to two backends in one transaction | refused |
| SQLAlchemy's psycopg 3 dialect | fails at connect; use psycopg2 |
| TLS | not supported |
| `COPY … FROM STDIN` | not supported; use `INSERT` batches |
| `DISCARD ALL` (pgbouncer's default reset) | refused; set `server_reset_query = 'RESET ALL; DEALLOCATE ALL'` |
| `SHOW <setting>` other than client parameters | refused |
| `SET GLOBAL`, `ALTER SYSTEM`, `ALTER ROLE … SET` | refused |
| Query cancel | answers, but the statement runs to its end |
| MySQL wire: generated id of a non-MySQL table | 0 |

## 13. Troubleshooting

| Error | Cause | Fix |
|-------|-------|-----|
| `FATAL 3D000` at connect | the database is not an alias, `alias.ns` or `local` | use one of those (section 5) |
| `no cast from oid to regtype` | SQLAlchemy's psycopg 3 dialect | its psycopg2 dialect |
| `a table is named connection.namespace.table` | four-part name, e.g. schema `"pg.shop.public"` | drop the database part: `pg.public` |
| `relation "alias.ns.t" does not exist` for a table that exists | first use of a new backend table, inside a transaction | run it once in autocommit (section 7) |
| `relation … does not exist` with a short name | the session has no place, or another one | the full three-part name |
| `keys, checks and defaults are not kept for a table of connection …` | an ORM's CREATE TABLE on a backend | create the table on the backend |
| `connection "…" only supports DDL in autocommit` | DDL inside a transaction | autocommit |
| `syntax error at or near "GENERATED"` | a framework creating its own table on OtterStax | an ordinary database for it (section 8) |
| `transaction already wrote to connection …` | two backends written in one transaction | one backend per transaction |
| `connection "<alias>" is unreachable` | backend down; retried after 10 s | check the backend |
