# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What This Is

A standalone two-RustFS stack plus fixtures used by the python integration suite. It
exists for two reasons:

1. **Manual debug** — start a local two-bucket S3 with `manual_run.sh` / the
   compose file and poke at it with `s3cmd.sh`. Useful for reproducing
   `conn::s3` issues without bringing the full test stack up.
2. **Fixture authoring** — `fixtures/` is checked-in seed data, also mounted
   into the docker integration test stack (the single-RustFS service defined in
   the top-level `compose.test.yml`) and read by `tests/test_*_mysql_{file,s3}.py`.

The old C++ semi-integration target (`test_s3_manager`) was removed. The s3 transfer
driver (`conn::s3::driver_t`) and its pools are covered by `tests/system/test_s3_errors.cpp`
(error paths, no object store) and end-to-end through the python integration tests
(`test_{schema_}mysql_s3.py`, `test_mysql_join_sql_s3_to_s3.py`,
`test_mysql_join_otb_local_s3.py`, `test_mysql_join_otb_local_s3_file.py`).

## Layout

- `docker-compose.yml` — two RustFS services (`rustfs1`, `rustfs2`) + one `*-init` job each that creates and seeds a bucket
- `fixtures/` — seed data. Two categories:
  - **Tiny C++-style fixtures** (`people.{csv,ndjson,parquet}`, `age.ndjson`) —
    5-row `id,name` shapes; held over from the removed `s3_integration.cpp`
    tests, still small enough to be useful for ad-hoc poking.
  - **Joinable python-integration fixtures** — `regions.parquet` (200 rows),
    `web_events.csv` (5000 rows), `campaigns.ndjson` (50 rows), all keyed on
    `campaign_id`. Regenerated by `fixtures/generate_external_fixtures.py`
    (seeded → reproducible; needs `pyarrow` + `faker`).
- `manual_run.sh` — `start` / `stop` debug helper; brings RustFS up and attaches
  it to the dev-container's external network so in-container code can reach it.
- `s3cmd.sh` — `ls` / `up` / `down` / `rm` helper wrapping `aws-cli` in a
  throwaway container.

## The Two Services

| Service | Host S3 API      | In-network     | Bucket          |
|---------|------------------|----------------|-----------------|
| rustfs1 | `localhost:9000` | `rustfs1:9000` | `test-bucket-1` |
| rustfs2 | `localhost:9010` | `rustfs2:9000` | `test-bucket-2` |

Both use `rustfsadmin`/`rustfsadmin`, region `us-east-1`. Two endpoints exist so
manual debug sessions can register two aliases at once and exercise per-alias
routing without changing the compose file.

## Gotchas

- The dev container runs on the external Docker network
  `otterstax_app_network_debug` (`.devcontainer/devcontainer.json`). Host-started
  RustFS is otherwise unreachable from inside; `manual_run.sh start` attaches the
  RustFS containers to that network with aliases `rustfs1`/`rustfs2`. Override the
  network via `DEVCON_NETWORK`.
- The `endpoint` field on `conn::s3::connect_params` triggers `scheme = "http"`
  and path-style addressing in `connectors/s3/manager.cpp::make_s3fs` — required
  for RustFS (and any other S3-compatible store). Leaving it empty would target real AWS.
- After editing `fixtures/`, re-run `docker compose ... up -d` so the `*-init`
  containers re-seed; a `down -v` wipes the bucket volumes.
- The python integration suite uses a separate RustFS service (in
  `compose.test.yml`, single bucket `test-bucket`). This `tests/s3/` stack is
  not used by `docker-run-tests.sh` — only manual debug.
- `s3cmd.sh` assumes the compose network name `s3_rustfs_network`
  (`<compose-dir>_<network>`). Override with `S3_NETWORK` if you used `-p`.
