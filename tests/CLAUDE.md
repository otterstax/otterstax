It turns `E` once an error inside the block failed it, from a pipeline's `Sync` and from a simple `Query` alike. The PG file's `read_failed_pipeline` asserts the protocol's error rule: after an error inside an extended-query pipeline the frontend sends the ErrorResponse alone, discards the pipeline up to its Sync, and the Sync answers exactly one ReadyForQuery with nothing trailing it (a failed simple Query keeps ErrorResponse + ReadyForQuery at once); the "named statement after a failure" case fails its Execute with an INSERT of a text literal into a bigint column, which the engine refuses when the statement runs (a repeated `CREATE TABLE` of an existing table is not an error). `test_flightsql_client_pg_backend.py` also asserts that a `$1` SELECT over the PostgreSQL backend is refused by GetFlightInfo with "unbound parameter" — the remote counterpart of the local refusal. The `*_client_mysql_backend.py` pair asserts remote DML row counts (`test_remote_dml_row_counts`) and that a DROP of a remote table neither the catalog nor MariaDB has is a "does not exist" error rather than a transport failure (`test_missing_remote_table_is_an_error_not_a_transport_failure`); `test_pg_client_pg_backend.py` also runs a CTE over a remote table, a remote table inside `IN (SELECT …)` / `EXISTS (SELECT …)`, and a column qualified with the table's whole four-part name (`SELECT products.pgdb.public.products.product_id FROM products.pgdb.public.products`); the `*_client_ch_backend.py` pair asserts ClickHouse's counts (INSERT from written_rows, mutations 0).

**Names and connections:** a remote table is written in four parts, `alias.db.schema.table` — `campaigns.db1.public.campaigns`, `impressions.db2.public.impressions`, `chtest.chdb.public.orders` (a MySQL / ClickHouse connection has the one schema `public`), `products.pgdb.public.products` (the PostgreSQL connection's configured schema); three parts are always a local `d.s.t`, two a schema of the session's database (`s.t`), so a file that makes local tables creates its schema first (`CREATE SCHEMA x` / `DROP SCHEMA x CASCADE`, `external_helpers.ensure_schema` before a `CREATE EXTERNAL TABLE x.t`). Every PostgreSQL client connects with `dbname="main"` (a database the engine does not have is `FATAL 3D000`); MySQL clients name no database (an unknown one is `1049`). `test_flightsql_client_mysql_backend.py` reads the streamed columns by position and asserts that `SELECT *` of a JOIN carries the key once per side (two `campaign_id` columns), as PostgreSQL answers it and as the engine, which runs every federated JOIN, streams it (the local-JOIN contract of `test_flightsql_client_otb_local.py`). The `*_client_mysql_backend.py` pair reads `SUM(campaign_length)` as the engine's BIGINT (an int on both wires, not MariaDB's DECIMAL text) and `SUM(budget)` over a FLOAT column as the engine's FLOAT, so that difference is checked to float32 precision; over the MySQL wire a FLOAT is read through a prepared (binary) cursor, since the text protocol writes it as MySQL does (six significant digits), and over the PG wire the float4 text is the shortest exact form, so the value is compared as a float32. GetTables lists the engine's local tables beside the remote ones: the `test_schema_*` files validate only the rows of their backend's catalogs (a remote table's catalog is `<alias>.<database>`: `campaigns.db1` / `impressions.db2`, `products.pgdb`, `chtest.chdb`), and `flightsql_e2e`'s `test_get_objects` requires the suite's own database among the catalogs and `federation` absent. MySQL-wire clients that write ask for `autocommit=True` (`external_helpers.conn_cfg` and the writers): the driver's `SET autocommit` reaches the engine and is the connection's own, so a driver with autocommit off opens a block with its first statement. Four files pin transactions and remote writes on the live stack: `test_transactions_pg_wire.py` (ROLLBACK / COMMIT seen from a second connection, two open blocks seeing only committed rows, an error failing the block with `25P02` until ROLLBACK, COMMIT of a failed block answered `ROLLBACK`, an extended-protocol BEGIN leaving psycopg INTRANS, psycopg with autocommit off committing and rolling back for real, SAVEPOINT / ROLLBACK TO / RELEASE taking a failed block back to its savepoint and SAVEPOINT outside a block `25P01`, a SET inside a block keeping it, `SET autocommit TO off` making that connection's INSERT open a block no other connection sees, a SET of an unknown parameter an error), `test_transactions_mysql_wire.py` (BEGIN / commit() seen by another connection with `SERVER_STATUS_IN_TRANS` while open, a block left open at close never committed, autocommit off opening a block at its first statement, `SET autocommit = 0` the connection's own, an error refusing the block's statements and its COMMIT committing nothing, SAVEPOINT / ROLLBACK TO / RELEASE inside a block, SET NAMES inside a block), `test_flightsql_client_tables_and_transactions.py` (GetTables with a local and a remote table and their columns, `federation` hidden; BEGIN by GetFlightInfo and by DoPut refused, COMMIT / ROLLBACK by text accepted) and `test_remote_row_dml.py`, which makes its tables on MariaDB and PostgreSQL directly (so it runs only inside the test network): a remote UPDATE / DELETE is pushed to the backend as one statement (a pushed MariaDB UPDATE counts matched rather than changed rows; no primary key is needed) or refused (`1235` / `0A000`, "cannot run as one statement") before anything is written; one whose WHERE is `id IN (SELECT id FROM <local table>)` is one statement too — the engine computes the uncorrelated sub-query and the backend gets `IN (<its values>)` — and changes exactly the rows it picks, on MariaDB, PostgreSQL and ClickHouse; RETURNING is refused on MariaDB and answers the written rows on PostgreSQL; an INSERT ... SELECT from a local table writes its rows; inside BEGIN a PostgreSQL / MariaDB write is undone on the backend by ROLLBACK and published by COMMIT, and a ClickHouse write is refused. `test_pushed_joins.py` makes its tables on ClickHouse, PostgreSQL and MariaDB directly too: a ClickHouse INNER and LEFT JOIN reading the second table's `Bool` (a boolean, NULL where the LEFT JOIN found no row), ORDER BY a name both tables have with LIMIT on ClickHouse and MariaDB (sorted by the output, not the left table's column, not refused as ambiguous), PostgreSQL DISTINCT ON over a JOIN of plain columns and over a grouped JOIN. `tests/scripts/startup.sh` runs all four and `test_pushed_joins.py`; a restart under another `config.yaml` (a connection taken out, a failed discovery, a MySQL server under `NO_BACKSLASH_ESCAPES`) has no python test because the suite runs one server image with the baked-in config; they are covered by `tests/system/test_restart_reconciliation.cpp`, `test_catalog.cpp` and `test_backend_discovery.cpp`.

The Spark Connect files — `test_spark_client_{mysql,pg,cross}_backend.py`, `test_spark_client_dataframe_ops.py` (DataFrame operations over `spark.table()` of both remote backends and of a local table, each checked against the same query written as SQL — the chains that read a derived table included: `select().count()`, `distinct().count()`, `limit().first()`, `groupBy().agg().select()`, a filter over an aggregate, `select().select()`, a `spark.sql` LIMIT under `limit()` — and `unionByName()` over reordered columns refused; `avg` over the local table's BIGINT column is checked against the DOUBLE mean of its rows, fraction kept), `test_spark_client_sql_and_show.py` (`spark.sql()` running its statement once: derived-table queries over the MySQL and PostgreSQL backends, `count()`, DDL and an INSERT that collecting their DataFrames does not run again; `df.show()` with its defaults, with the footer, untruncated, vertical and over a `spark.sql()` query, against text rebuilt by Spark's rules) and `test_spark_client_catalog.py` (`spark.catalog` over both remote backends and a local database made through `spark.sql()`) — are not in the standard suite (`test-client`). ## Running a Single Test

```bash
# Run one Catch2 test by name
./build/test_system "[test name]"

# List all available test names
./build/test_system --list-tests

# Run with verbose output
./build/test_system -s
```

Catch2 splits a test-name filter on commas, and shell quoting does not help:
Catch2 splits the spec itself, and a spec whose own `"` quotes hold a comma is
refused outright (`Invalid Filter`). A name that contains a comma therefore
runs only with the comma backslash-escaped, by a comma-free `*` fragment, or by
its tag:

```bash
./build/Release/tests/unit/utility/test_utils 'parse_port: out-of-range values are invalid_parameter\, not truncated'
./build/Release/tests/unit/utility/test_utils 'parse_port: out-of-range values are invalid_parameter*'
```

Give a new case a comma-free name so it stays runnable exactly as it is
written; every case in the table below carries none. Many older names
across the suites do contain one — the two forms above are how to run those.

## Engine-defect tags (`[engine-defect-*]`)

A test that pins a defect of the **otterbrix engine** — or of actor-zeta, the actor
runtime it ships with (`otb-notify`) — is tagged `[engine-defect-<id>]`. A case is

it and `catch_discover_tests` from registering it, so neither `ctest` nor the
`Dockerfile.test` build sees it) only while its defect is open; every visible case
below runs in the default run and in `ctest` and is green. A red visible case is an
engine regression: fix the engine, do not re-hide the tag.

## Python Test Structure

Python tests share common helpers via `config.py` (connection params) and `query_data.py` (expected result fixtures). File names encode: `test_{protocol}_client_{backend}_backend[_mutable].py`. The `test_cross_backend_queries*.py` files exercise mixed-backend joins.

External-table tests (s3/file grammar extension) over the MySQL wire — driven via the shared `external_helpers.py` module and a small family of `test_mysql_*.py` files:

- `test_{schema_,}mysql_{file,s3}.py` — the originals; verify schema discovery, row counts, per-campaign aggregates, `COPY` round-trips, and JOINs across the two joinable fixtures `regions.parquet` (200 rows) and `web_events.csv` (5000 rows).
- `test_mysql_file_ndjson.py` — adds `campaigns.ndjson` (50 rows) to confirm ndjson load + COPY round-trip via the file source.
- `test_mysql_join_sql_s3_to_s3.py` — full federated → external round-trip: `CREATE EXTERNAL TABLE` from s3 parquet, stage backend rows into otterbrix-internal, JOIN, persist, `COPY (…) TO 's3://…'` as csv, read back via a fresh external table.
- `test_mysql_join_otb_local_s3.py` — `CREATE TABLE` + `INSERT VALUES` into otterbrix-internal then JOIN against an s3-loaded external; positive control for the "all sides resolved to engine-internal tables" path.
- `test_mysql_join_otb_local_backend.py` — backend on the LEFT, otterbrix-internal `CREATE TABLE` on the RIGHT, JOIN on a STRING key. Mirrors the shape `examples/demo/sql/step_4.sql` runs in the live demo: the engine reads the backend table through the federation (its storage's scan; a JOIN with a local table is not pushed down) and JOINs it against the engine-resident rows in-process. The string JOIN key avoids the int width sensitivity described under "JOIN-key width sensitivity" below.
- `test_mysql_join_otb_local_s3_file.py` — three-origin JOIN: s3 parquet `regions` ⋈ local file csv `web_events` ⋈ otterbrix-internal `weights` (`CREATE TABLE`+`INSERT VALUES`), all on `campaign_id` (int64 on every side). Smaller-scale shadow of the `external_join_all` benchmark — catches regressions in the "everything resolved to engine-internal" multi-source JOIN before the benchmark suite runs.

Fixtures live in `tests/s3/fixtures/` (regenerable by `generate_external_fixtures.py`; needs `pyarrow` + `faker`). The python suite uses the single-bucket RustFS in `compose.test.yml` (service `rustfs`, seeded by `rustfs-init` with `aws-cli`) (mount `/fixtures` for local-file mode; for s3 mode the `rustfstest` alias is registered at server startup from the baked-in `tests/scripts/config.yaml`, so `ExternalTableTester.ensure_credentials()` is a no-op). The standalone two-RustFS debug stack under `tests/s3/` (`docker-compose.yml`, `manual_run.sh`, `s3cmd.sh`) is unrelated to the suite — see `tests/s3/CLAUDE.md`.

**JOIN-key width sensitivity** is the common gotcha in the JOIN tests
above. The engine silently returns zero rows when an equi-JOIN compares an
int32 column against an int64 column — no error. Two places to keep in
sync:

- Local `CREATE TABLE` columns joining against parquet-loaded data: declare
  the local side `bigint` to match the int64 the parquet loader emits.
- Backend `INT` columns (which `mysql_to_chunk` and friends pass through as
  int32) joining against a local `bigint`: either stage the backend slice
  into a local `bigint` table first (`test_mysql_join_sql_s3_to_s3.py`) or
  join on a string column instead (`test_mysql_join_otb_local_backend.py`,
  mirroring `examples/demo/sql/step_4.sql`). The engine-side rule is stated
  in the top-level `CLAUDE.md`, "JOIN-key type widths must agree".

**Cleanup discipline.** `ExternalTableTester.cleanup()` runs DROPs for every
`(db, table)` pair the test appended to `_created`. Most tests in this
family call it at the **end** of `run()` rather than from a `try/finally`,
so a failed `assert` skips the cleanup and leaves engine state behind. That
leak can cascade into the next test in the suite (we hit a 400-row
`regions` count in one run because the previous test failed before
cleaning up). Wrap with `try/finally` when you add a new test here.

Run a single Python test file:
```bash
python -m pytest tests/test_flightsql_client_mysql_backend.py -v
```
(Requires live Docker stack — run `docker compose -f compose.test.yml up -d` first. Connections are baked into the otterstax image from `tests/scripts/config.yaml` and registered at startup; no manual registration step.)

### Convention: one class, each case an explicit `test_*` method

**Do NOT cram every scenario into one giant `main()` with inline blocks — it is unreadable.** Structure an integration test file as a single class whose cases are named methods. Reference: `test_pg_client_pg_backend.py` and the `test_kafka_*.py` family.

- One `class <Name>Test` per file; connection params / topic names / fixtures in `__init__` (read `--local` host via `config.py`).
- `setup(self)` creates the shared objects (CREATE TABLE/SOURCE/STREAM, produce seed data); `cleanup(self)` drops them and closes the connection.
- **Each test case is its own `def test_<behaviour>(self)` with a one-line docstring** — one observable behaviour per method, named for what it asserts.
- Shared helpers (`create_topic`, `consume`, `assert_equal`, …) are methods on the class, not free functions duplicated inline.
- `run_all_tests(self)`: `try: setup(); test_a(); test_b(); finally: cleanup()`. **Let exceptions propagate** — do not `except: print("fail")` and swallow, or the green ALL-PASSED banner will lie (a real bug in some older tests).
- `main_test()` parses `--local`, runs `run_all_tests()`, prints the pass/fail banner, returns `0`/`1`; `sys.exit(main_test())` at the bottom.
(Requires live Docker stack — run `docker compose -f compose.test.yml up -d` first. Connections are baked into the otterstax image from `tests/scripts/config.yaml` and registered at startup; no manual registration step.)
