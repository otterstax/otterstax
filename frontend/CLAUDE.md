# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Role

`frontend/` implements the three wire-protocol servers and the Spark Connect gRPC server. Each server accepts client connections, receives SQL (Spark Connect also DataFrame plans), runs it on the connection's own query session (`session::query_session_t`, opened from the `session_factory_t` the servers share), and streams results back.

## Structure

```
frontend/
├── common/               — shared CRTP base server + connection base
├── flight_sql/           — the in-house Flight SQL server (port 8815)
├── mysql_server/         — MySQL wire protocol (port 8816)
├── postgres_server/      — PostgreSQL wire protocol (port 8817)
└── spark_connect_server/ — Spark Connect gRPC server for PySpark clients (port 15002)
```

## Common Layer (`frontend/common/`)

`frontend_server<DerivedConnection>` is a CRTP template that manages a connection pool (max 1000 slots), a `thread_pool_manager` (Boost.Asio) of `frontend_server_config::pool_size` threads, and async accept/reject logic. No server sizes itself from the machine: `main.cpp`, which owns the four servers (declared after the session factory, so destroyed — each stopping in its destructor — before it), resolves every server's threads from `service.runtime` (`mysql_io`, `postgres_io`, `flight_sql_io`, `spark_connect_io`; 0 = `max(2, hardware threads)`, `runtime::resolve_threads`) and hands them down — `frontend_server_config::pool_size`, `flight::server::config_t::threads`, `SparkConnectServerConfig::io_threads` have no default and refuse 0 (asserted), and neither has `thread_pool_manager`. A MySQL / PostgreSQL connection holds a thread of its server's pool while its statement runs (the bridge waits on it), so `mysql_io` / `postgres_io` bound the statements in flight over that wire. `DerivedConnection` must implement:
- a constructor `(std::pmr::memory_resource*, tcp::socket&& accepted, uint32_t id, otterstax::session::session_factory_t& sessions, connection_close_sink&, size_t slot, std::chrono::milliseconds read_timeout)` — it takes over a socket that is already accepted and already on its own strand, and opens its query session from `sessions` (`frontend_server_config::sessions`)
- `start()` — begins protocol handshake
- `finish()` — signals clean shutdown
- `static build_too_many_connections_error()` — protocol-specific rejection packet

`frontend_connection` provides the base connection class with shared utilities (`packet_reader_base`, `packet_writer_base`, `resultset_utils`).

A connection announces its own close through the `connection_close_sink`
interface (`release_connection_slot(slot)`), which a member of `frontend_server`
(`close_sink_`) implements to free the pool slot — a plain virtual call, no
type-erased callback. It is a member and not a base class: the pool's threads run
until `stop()` in the server's destructor body, and a base's vptr is rewritten as
its destructor starts, so a connection's last completion raced the server's
teardown on the vptr (TSAN); a member is destroyed only after the body joined the
pool.

**Connection lifetime (`frontend_connection`).** Each connection's socket runs
on its own asio strand — the acceptor accepts into a socket created on
`make_strand(ctx)` and the connection takes it over — so every completion and every
touch of the connection's members after construction happens on that strand,
one at a time (`start()` posts `start_impl` there). Every asio operation the
connection starts — read, write, the idle timer, a posted lambda — goes
through `safe_callback`, which counts it in `pending_ops_` and decrements once
the handler has run. `finish()` is callable from any thread and idempotent
(`finish_requested_` gate); it posts the close onto the strand, where the
socket is closed and the timer cancelled (`closed_`), so every outstanding
operation completes with `operation_aborted` (handlers that see `closed()`
return quietly). The connection is destroyed exactly once, by the completion
that brings `pending_ops_` to zero after the close has run: it calls
`finish_impl()` and then `release_connection_slot(slot)`. Nothing captures
`this` in a handler that can outlive the object, and no `shared_ptr` is
involved. Buffers handed to `async_write` are members (`send_buffer_`, the
server's `reject_packet_`), never locals. The idle timer is a member
(`read_timer_`), armed by `arm_read_timeout(stage)` before each read and
cancelled by the read's completion; a generation counter ignores a timer
completion that belongs to an earlier arm. Its duration is
`frontend_server_config::read_timeout` (no default; `main.cpp` passes
`CONNECTION_TIMEOUT_SEC`). The PG `StartupMessage` body is read through
`ensure_read_buffer` (bounded by `MAX_BUFFER_SIZE`), never past the 4 KiB
initial buffer. `tests/system/test_frontend_connection_lifetime.cpp` pins all
of this over raw client sockets: `stop()` with attached clients, the idle
timeout, a client dropping the socket mid-read, an oversize startup message.

**Shutdown contract (`frontend_server::stop()`).** `stop()` sets `stopped_`,
then under `pool_mutex_` closes the acceptor, cancels the accept retry timer and
finishes every pooled connection, and joins the pool. `finish()` closes the
socket on the connection's strand and the completion of the last pending
operation releases the slot — the only path that destroys a pooled connection.
A connection exists only for a socket that was already accepted: the accept
chain (`accept_connections()`) accepts into a socket asio creates on a fresh
strand and hands it to `admit()`, which pools a connection for it or refuses
the client. So `stop()` never touches a socket an accept is still writing
into — asio assigns the accepted descriptor to the peer socket on the io thread
before it calls the handler, and closing a pre-built connection's socket under
a pending accept was a data race (TSAN: `do_assign` against `close`). The accept
is armed, and `admit()` pools, under `pool_mutex_` after checking `stopped_`:
once it is set nothing is armed or pooled — an accept re-armed on the closed
acceptor completes at once with an error, and re-arming from there spins the
pool threads forever. A refusal (pool full) owns its socket: it writes the
too-many-connections packet (`reject_packet_`, read-only) and the socket closes
when the write completes, so any number can be in flight and none shares state
with the chain. When building the connection throws, the catch in `admit()`
hands back the slot it took (still empty — left taken, `MAX_CONNECTIONS`
failures would fill the pool and every later client would be refused) and
pauses the chain on the member `accept_retry_timer_` for
`frontend_server_config::accept_retry_delay` (no default; `main.cpp` passes
`ACCEPT_RETRY_DELAY_MS`, 100 ms). The pause holds the client's socket and then
admits the same client again: the constructors take the socket by rvalue
reference, so a throw before the base connection took it leaves it with the
server, and the client is served late rather than dropped. There is one accept
chain, re-armed only from its own completions, so one timer serves it. The
pause is armed under `pool_mutex_` only while `stopped_` is clear, and `stop()`
cancels the timer under the same lock: a pending retry completes with
`operation_aborted`, does not re-arm, and the socket it holds closes with it.
`local_port()` answers the bound port (tests bind port 0).
`tests/system/test_frontend_shutdown.cpp` pins this with start/stop cycles on
both servers; `tests/system/test_frontend_accept_retry.cpp` pins the retry (a
connection whose constructor throws on chosen attempts: the client the failures
were for is served after the pauses and the chain keeps accepting, `stop()` with
the retry pending returns and closes the waiting client, a client is served
after more failures than the pool has slots);
`tests/system/test_frontend_connection_lifetime.cpp` pins `stop()` with clients
attached, which is where TSAN saw both races.

`asio_future_bridge.hpp` is the universal sink between the query sessions
(which hand back `actor_zeta::unique_future`s) and the per-connection asio
executor: `async_await_future` polls `take_ready()` from inside a coroutine and
co_returns the `core::result_wrapper_t<session_payload>` when ready, never
blocking the executor thread; `await_future_blocking` drives it on a private
`io_context` for a handler that has no coroutine of its own. Both take the
memory resource every message they create lives on. Both answer an
`awaited_t<T>` — the session's `result_wrapper_t<T>` plus how the await ended,
`await_status_t`: `answered` (the result is the session's own, success or error),
`timed_out` (the deadline passed first — the frontends map it to their protocol's
"query cancelled" error) or `broken` (no value arrived: the actor runtime closed
the channel, or an exception escaped a coroutine of the chain — actor-zeta stamps
`errc::interrupted` on such a future (the exception itself is reachable only by a
throwing `take_ready()`; asked of actor-zeta as AZ-exception,
`docs/proposals/actor-zeta.md`), and the bridge's message says that the
statement failed without an answer instead of "Interrupted system call"; MySQL
answers it `ER_UNKNOWN_ERROR` and fails an open block behind it, as for a timeout). A
frontend tells the bridge's failures from the session's by that status
(`timed_out()`), **never by an error code**: the engine answers with every code
the bridge could pick for itself (`transaction_inactive` among them,
`manager_dispatcher_t`'s BEGIN that reached no transaction), and such an answer
must reach the client as the engine's error.
**A timed-out statement is not cancelled** (the engine has no cancel): it runs
on to its end. Inside an explicit transaction the frontend therefore fails the
block behind it — `query_session_t::fail_transaction`, sent without awaiting it,
queued after the statement and ahead of whatever the client sends next — so a
COMMIT cannot publish what the client was told is cancelled (PG
`send_error_response`, MySQL `answer_await_failure`, Spark `fail_unanswered`).
A `broken` await is handled the same way on every frontend — the session never
settled the statement — with the reason `otterstax::unanswered_block_failure`
gives for either status (PG `send_error_response`, MySQL `answer_await_failure`,
Spark `fail_unanswered`).
Outside a block an autocommit statement that times out still commits on its own.
The Spark Connect handlers cannot use it — their coroutines run on an
`agrpc::GrpcExecutor` — and await through its gRPC form,
`spark_connect_server/await_future.hpp`, under the same contract (see below).

## FlightSQL (`flight_sql/`)

The in-house Flight SQL server — **no Arrow Flight dependency, but the PROJECT's
arrow core for the data plane**: gRPC handlers written as asio-grpc coroutines
(`rpc/flight_server.cpp`) over the vendored `Flight.proto` / `FlightSql.proto`
(`format/`). The protocol core (`core/`) owns the ticket registry, the prepared
statements and the engine itself — there is no engine interface: the server has
exactly one engine, and `FlightSqlCore` owns it (`session_engine.*`,
`SessionEngine` over the session factory; every session call awaited through the
common `asio_future_bridge`, the same bridge the wire frontends use). The exchange
shapes live in `core/core.hpp` next to their only consumers; the metadata
carries the PROJECT's `table_info` (utility/table_info.hpp), not a protocol twin.

Layers: `flight_sql_proto` (generated protobuf + gRPC stubs), `flight_sql_core`
(commands, auth, ticket manager) and `flight_sql` (the server: rpc handlers +
`SessionEngine`). Every conversion goes through the project's own
translators — `tsl::to_arrow_schema` / `chunk_to_record_batch` /
`arrow_to_chunk` — the same ones the file paths use; serialization is
`arrow::ipc` (`GetRecordBatchPayload` / `SerializeSchema` /
`RecordBatchStreamReader`), with a ~15-line framing glue in
`rpc/flight_server.cpp` (`append_encapsulated`) — the only wire-format code we
own.

- **GetFlightInfo / GetSchema materialize the result**: the engine
  runs the query and the result is serialized for the wire
  (`core::materialize`). GetFlightInfo (and PollFlightInfo) cache it under an
  opaque ticket (`otterstax-tickets/<32 hex>`) and DoGet streams the cached
  batches; GetSchema answers the schema and keeps nothing (it hands out no
  ticket). There is no two-phase prepare/ticket handshake. **A ticket is single
  use** (Flight.proto, `Ticket`): DoGet takes the result out of the cache
  (`FlightSqlCore::take_result`) and is its only owner for the length of the
  stream (`CachedResultPtr` is a `std::unique_ptr`: the RPC that materialized
  it, then the cache, then the DoGet — the FlightInfo is built before
  `register_result` takes it, its ticket set after, `set_flight_ticket`), so a
  result lives from GetFlightInfo to its DoGet and no longer, and an eviction
  never frees what a DoGet streams; a second DoGet of the ticket is
  `NOT_FOUND`. What is never redeemed (a client that read only FlightInfo, or
  went away) is bounded by count and by bytes (`kDefaultResultCacheLimits`:
  1024 results, 256 MiB; the oldest evicted first, the result just registered
  never). The cache used to keep every result until 1024 newer ones pushed it
  out — DoGet released nothing — so the server grew by every result it served
  (62 → 124 MB over 800 benchmark RPCs) and DoGet streamed from a raw pointer
  an eviction could free. `tests/system/test_flightsql_tickets.cpp` pins it.
  A prepared statement's state (`PreparedStatementState`, the entry's value) is
  copied out under the core's lock by a lookup — the arrow schemas and batches
  inside are arrow's shared buffers — and a bind replaces the entry's bound
  rows, so a bind racing an execution never changes what it reads.
  **Tickets and prepared-statement handles are unguessable and bound to their
  client.** Each is `FlightSqlCore::kIdBytes` (16 = 128 bits) of
  `frontend::secure_random_hex` behind its prefix (`otterstax-tickets/`,
  `otterstax-prepared/`); without secure bytes GetFlightInfo /
  CreatePreparedStatement fail `UNAVAILABLE` (the handle is drawn before the
  statement is prepared). They used to be counters (`<n>-<hash of n>`,
  `otterstax-prepared/<n>`), so another client could DoGet someone else's
  result or run / bind / close someone else's statement. Every entry records
  its owner, `AuthService::client_of(ctx)` — the SHA-256 of the caller's
  bearer token with configured credentials, the empty string on an anonymous
  service (every client one owner, protected by the 128 bits alone) — and
  `take_result` / `prepared_lookup` / `prepared_bind` / `close_prepared` (and
  `execute_descriptor` for a `CommandPreparedStatementQuery`) answer another
  client's id `NOT_FOUND`, exactly as an unknown one, leaving it untouched (a
  foreign DoGet does not consume the ticket). The lookup is the hash table's.
  `tests/system/test_flightsql_tickets.cpp` pins the format, uniqueness and the
  foreign ticket / handle refusals.
- **The adapter converts `session_payload` through `tsl::to_arrow_schema` +
  `chunk_to_record_batch`**: nested STRUCT/LIST result columns are refused
  (`EngineError` → `INVALID_ARGUMENT`) where the schema is handed out; a
  column the wire cannot carry is refused the same way. `GetRecordBatchPayload`
  bodies are padded per buffer (the serializer delivers unaligned buffers —
  the stream writer's alignment is ours to apply).
- **Prepared statements** are the full cycle: `CreatePreparedStatement`
  (prepare through `query_session_t::prepare_schema`), DoPut bind (an Arrow
  batch of parameters — read with the in-house IPC reader), execute. **Session
  scope:** a statement run by text (GetFlightInfo, DoPut update) runs on a query
  session of its own, closed when the RPC returns (autocommit); a prepared
  statement keeps ONE query session from `CreatePreparedStatement` to
  `ClosePreparedStatement`, owned by the statement's entry in
  `FlightSqlCore::prepared_` (a `session_ptr`, its only owner: `SessionEngine::prepare()`
  opens it and hands it over). Every execution (`FlightSqlCore::execute_prepared` /
  `execute_update_prepared`), in whatever RPC and on whatever gRPC thread, runs
  on it one at a time: each step finds the entry under the core's lock and only
  queues its statement there (`FlightSqlCore::use_prepared`, by the statement's
  handle: `SessionEngine::execute_prepared` / `execute_update_prepared` take the
  core and the handle), then awaits outside the lock. `close_prepared` erases the entry under the same lock, which closes
  the session: a statement it took runs to its end, and an execution the close
  cut short (a later step, or a statement the closed session answered
  `connection_closed`) answers `NOT_FOUND`, as an unknown handle — never a
  session freed under it (`tests/system/test_flightsql_session_scope.cpp`,
  "a close racing executions"). Session statements are single-use, so every
  execution re-prepares on that session under a fresh statement id. No scope outlives what it runs, so a transaction
  opened in one could never be ended by the client: a statement that leaves the
  session inside a block (BEGIN, by text or prepared) is rolled back and refused
  (`SessionEngine::refuse_open_transaction`, "a transaction cannot be opened over
  Flight SQL"). `tests/system/test_flightsql_session_scope.cpp`
  pins both scopes through `live_sessions()`, and the BEGIN refusal. The parameter schema handed out is int64 fields `$1..$N` (the
  model the reference drivers bind against); bind batches are read with
  `arrow::ipc::RecordBatchStreamReader` and converted through the project's
  `tsl::arrow_to_chunk`. executemany of an UPDATE runs one execution per bound
  row, the affected counts sum. SqlInfo's `value` is a dense union whose
  values live in the CHILD builders (`DenseUnionBuilder::child_builder`) —
  appending to a builder that is not the child leaves the union INVALID.
- **Metadata** (Catalogs / DbSchemas / Tables / TableTypes / SqlInfo) answers
  from one listing (`SessionEngine::metadata`): five reads through a query
  session — `pg_catalog.pg_namespace` / `pg_class` / `pg_attribute` and
  `federation.remote_tables` / `remote_columns` (the last of each pair only with
  `include_schema`) — handed to `catalog::list_tables` (`catalog/introspection.hpp`;
  `get_tables_command_t` — the Flight SQL filters decoupled from any wire
  library). Local tables are listed under their database with an empty schema,
  remote tables as the backend spells them (remote database, remote schema);
  the federation metadata tables and the Kafka bookkeeping tables are hidden.
  GetCatalogs answers every catalog once and GetDbSchemas every (catalog,
  schema) pair once under its own catalog, both in the spec's order (catalog,
  then schema; `EngineMetadata`, deduplicated in `SessionEngine::metadata`);
  GetDbSchemas and GetTables apply `catalog` (exact match) and
  `db_schema_filter_pattern` (LIKE), GetTables also its table name and type
  filters (`catalogs_batch` / `db_schemas_batch` / `tables_batch`,
  `core/commands.hpp`).
- **Auth** is anonymous by default (`AuthService::anonymous`); the extension
  point for configured credentials is `AuthService::basic` (Handshake Basic →
  Bearer in initial metadata).
  **The bearer token is `AuthService::kTokenBytes` (32 = 256 bits) of
  `frontend::secure_random_bytes`, lower-case hex (64 chars).** It used to be
  an `mt19937_64` draw seeded with 32 bits of `random_device` plus a counter —
  recoverable from one token, so a client could predict the others. When no
  secure bytes can be had the Handshake fails `UNAVAILABLE` and no token is
  issued (never a weaker one). Only the SHA-256 digests of issued tokens are
  kept (`token_store_t`, under a `shared_mutex`: the Flight server runs its
  handlers on several threads, a Handshake inserts while other RPCs look up);
  `verify_bearer` looks the presented token up by its digest and confirms with
  `CRYPTO_memcmp`, and the Basic user / password are compared the same way
  (digests, constant time, both checked whatever fails first). An anonymous
  service still issues a token but records none. The random source is
  injectable (`AuthService::basic(user, password, random_source)`) so
  `tests/system/test_flightsql_auth.cpp` can pin the `UNAVAILABLE` refusal next
  to the token's format, uniqueness and the refusal of a token it did not issue.
- `main.cpp` drives it (`start` — false refuses startup, return 1 — then `run`): `flight::server::flight_sql_server` binds the port,
  runs the `GrpcContext` on N threads (`service.runtime.flight_sql_io` — `SessionEngine`
  blocks its calling thread for the length of a query, so N bounds its queries in flight), and a signal thread
  (SIGINT/SIGTERM) stops the grpc server and the context; `run()` returns and
  the common shutdown sequence follows. `ListFlights` / `DoExchange` are
  `UNIMPLEMENTED`; IPC compression (lz4/zstd) is not supported — clients do
  not send it by default.

Acceptance: `tests/system/test_flightsql_schema_contract.cpp` (the
GetFlightInfo/DoGet contract through a real session stack), `tests/system/test_flightsql_session_scope.cpp`, `tests/system/test_flightsql_metadata.cpp` (the metadata answers) and
`tests/flightsql_e2e/` — the original Apache drivers (pyarrow, ADBC, the Go
`database/sql` driver in `tests/flightsql_go/`) against the live server, plus
the 8 `tests/test_*flightsql*.py` suites.

## MySQL / PostgreSQL Servers

Both follow the same pattern: `frontend_server<XConnection>` accepts TCP connections; each connection implements the respective handshake + query/response protocol, then sends `query_session_t::execute` (and friends) to its own query session — one per connection (`session_` member, a `session_ptr`) — which returns an `actor_zeta::unique_future<core::result_wrapper_t<session_payload>>`. The connection awaits that future via `frontend/common/asio_future_bridge.hpp::await_future_blocking` (polls `take_ready()` on a private asio executor — no blocking get, no shared state). The FlightSQL `GetTables` path goes the same way: its five reads are session statements.

**Prepared statements are single-use on the session side.** `query_session_t::execute_prepared_statement` drops the statement after one execution, successful or not, and answers a second one with `invalid_parameter` ("prepared statement must be re-prepared"). Both frontends therefore keep the accepted SQL text in their statement metadata (`prepared_stmt_meta::sql`, `consumed`) and, for every `COM_STMT_EXECUTE` / `Execute` after the first and after any failed one, run `query_session_t::prepare_schema` again under a fresh statement id (`query_session_t::next_statement()`) before executing.

**Closing a statement releases the session entry.** MySQL `COM_STMT_CLOSE` and PG `Close(statement)` — and a PG `Parse` that replaces a statement of the same name, the unnamed one included (`do_close`) — send `query_session_t::close_statement` for the statement's current statement id when the statement is not `consumed` (a consumed one the session has already dropped), then forget the frontend entry. The close is awaited through the bridge like every other session call; a failure is logged (`warn`), never turned into a protocol error — MySQL sends nothing (protocol), PG answers `CloseComplete` as before. A MySQL `COM_STMT_PREPARE` refused by the frontend after the session stored the statement (an unencodable column, below) closes it the same way before the error packet goes out. **In an aborted block a `Parse` and a `Bind` are refused at once**, as PostgreSQL's `exec_parse_message` / `exec_bind_message` refuse them: `25P02` answers the message itself (never a `ParseComplete` / `BindComplete`) for anything but a statement that ends the block (`session::is_transaction_exit_statement`: COMMIT / END, ROLLBACK / ABORT, ROLLBACK TO, PREPARE TRANSACTION, read off the raw tree; a Bind of one without parameters) or an empty text (`block_aborted`: the session's failed block, or a failure sent to it and not yet seen applied). **PG `DEALLOCATE [PREPARE] <name> | ALL`** is the frontend's too, on both routes: read off the raw parse tree (`session::deallocate_statement`, `session/statement_kind.hpp` — never off the text, and never sent to the session: the engine's transformer has no DeallocateStmt; only a text whose first keyword is DEALLOCATE is parsed for it, so every other `Query` is parsed once, by the session), `run_deallocate` drops the named statement, or every named one (`drop_statement`: the session entry released, the frontend entry forgotten) and leaves the portals bound from it open, as PostgreSQL's DEALLOCATE does (a portal holds its statement, `statement_ptr`, and prepares the text again at its Execute) — unlike `Close(statement)` / a replacing `Parse` (`do_close`), which close the statement's portals as the protocol says. An unknown name is `26000` (`prepared statement "<name>" does not exist`), and a failed block refuses it with `25P02`, as PostgreSQL does. The simple `Query` route (`handle_deallocate`) answers `CommandComplete DEALLOCATE` / `DEALLOCATE ALL` and `ReadyForQuery`; on the extended route a `Parse` of it keeps the statement in the frontend (`prepared_stmt_meta::deallocate`, tag `T_DeallocateStmt`, no session entry), `Describe` answers `NoData` and `Execute` runs it and answers the `CommandComplete`. psycopg sends `DEALLOCATE ALL` by itself after every `ROLLBACK` / `DROP` / `ALTER` while it holds prepared statements — through `Parse` / `Bind` / `Execute` in pipeline mode — so without it the client saw those statements fail.

**Ending a connection closes its query session.** `frontend_connection::finish()` is the single teardown point of a connection (client `COM_QUIT` / `Terminate`, socket drop, protocol error, read timeout, FATAL error, `frontend_server::stop()`); its posted lambda closes the socket, and the completion that brings the pending-operation count to zero calls the derived `finish_impl()`, then releases the pool slot. `mysql_connection::finish_impl` / `postgres_connection::finish_impl` clear the frontend's statement maps and drop the `session_ptr`, which closes the session: every unexecuted prepared statement goes with it, and a statement still in flight finishes on the sessions pool before the session frees itself (`session/CLAUDE.md`, "the close protocol"). Nothing waits on the connection's side, so a client may drop its socket mid-statement; `tests/system/test_frontend_transactions.cpp` ("wire disconnect") pins that the server keeps serving and the session is freed once the statement ended, and `tests/test_pg_extended_protocol.py` / `tests/test_mysql_wire_protocol.py` that the path completes for Terminate / `COM_QUIT` and a bare socket drop.

**Transactions.** Each connection's session owns one engine session, so `BEGIN` / `COMMIT` / `ROLLBACK` over engine tables work on both wires with PostgreSQL semantics (`session/CLAUDE.md`). **The block comes from one place, the session** (`query_session_t::transaction_state()`, read after each awaited statement): PG's ReadyForQuery status (`ready_status()`: `I` / `T` / `E`) on the simple `Query`, on the `Sync` of the extended route and after any error alike; there is no frontend transaction state machine and no statement text is parsed to follow the block. A statement refused with `transaction_finalized` inside a failed block is answered `ErrorResponse 25P02` (`IN_FAILED_SQL_TRANSACTION`) on every route; a COMMIT of a failed block (the engine rolled it back; told by that code and the session's block being idle afterwards, `query_session_t::ended_failed_block`) is answered `CommandComplete ROLLBACK` and `I`, by `Query` and by `Execute` alike. The CommandComplete tag of BEGIN / COMMIT / ROLLBACK is the session's (`session_payload::transaction`). A failure the PG frontend finds itself (a malformed message, a Bind it refuses, an unencodable column, a statement it stopped waiting for) fails an open block as in PostgreSQL: `send_error_response` reports it to the session (`fail_transaction`, not awaited) and reports `E` until an answer shows it applied (`failure_pending_`). **SAVEPOINT / RELEASE / ROLLBACK TO** are refused: otterbrix has no savepoints and its transformer refuses them as `unimplemented_yet` "unsupported transaction statement", which PG answers `0A000` and MySQL `ER_NOT_SUPPORTED_YET` — by the code, never the text; like every error inside a block the refusal fails it, outside a block it fails nothing. (The old frontend "emulation" answered them as success without undoing anything — a `ROLLBACK TO` that did not roll back — and is gone.) MySQL answers a refused statement with an ERR packet carrying the engine's text and a COMMIT of a failed block with an OK packet (`answer_failed_commit`, by `query_session_t::ended_failed_block`). **Every MySQL OK and EOF packet carries the session's block** (`status_flags()`): `SERVER_STATUS_AUTOCOMMIT`, plus `SERVER_STATUS_IN_TRANS` while the session is inside a block, open or failed, until ROLLBACK / COMMIT ends it — what MySQL clients read `in_transaction` from. **`SET NAMES <charset> [COLLATE …]`** (every MySQL connector sends it after the handshake) is the frontend's own (a MySQL protocol statement, below): OK for a utf-8 charset (`utf8mb4`, `utf8mb3`, `utf8`), `ER_HANDSHAKE_ERROR` otherwise — so inside a block it is neither refused by the engine nor fails the block behind the OK the client was given. Any other `SET` / `RESET` (`SET autocommit = 0` among what connectors send after the handshake, `SET timezone`, any parameter) is answered by the query session OK without effect, on every protocol — it never reaches the engine, which would apply it to every connection (`session/CLAUDE.md`); the PG CommandComplete tag is `SET`. The MySQL frontend recognises a SET of system variables in MySQL's own forms and sends it to `query_session_t::execute_setting` without its text (the engine's grammar reads neither `@@`, `GLOBAL` nor several assignments): the session's answer, the same as for every SET — OK, in a failed block refused. A `COM_STMT_PREPARE` of a statement the engine does not support (SAVEPOINT / RELEASE / ROLLBACK TO) is `ER_NOT_SUPPORTED_YET`, by the code, as `COM_QUERY` answers it; a prepare whose text does not parse is `ER_SYNTAX_ERROR` and fails an open block, as PostgreSQL's own Parse error does. One mapping, `send_statement_error`, answers a statement the session refused on `COM_QUERY`, `COM_STMT_PREPARE`, `COM_STMT_EXECUTE` (the execution and the re-prepare in front of a later one, `reprepare_stmt`, which answered `ER_UNKNOWN_ERROR` before) and a SET: `unimplemented_yet` is `ER_NOT_SUPPORTED_YET` (1235), every other code `ER_SYNTAX_ERROR` (1149) — a missing table included (`tests/system/test_frontend_mysql_protocol.cpp`, "a refused statement's errno"). `tests/system/test_frontend_transactions.cpp` covers ROLLBACK / COMMIT visibility from a second connection, the abort-until-ROLLBACK rule on both wires, the extended route's ReadyForQuery, a frontend error failing the block, and SAVEPOINT.

**MySQL protocol statements** (`mysql_server/protocol/`). What MySQL clients and drivers send on their own — at connect, around a transaction, before a commit — is answered by the frontend, because the engine reads PostgreSQL's grammar, which has no `@@variable`, no SHOW VARIABLES / SHOW WARNINGS and no MySQL SET forms (`SELECT @@version_comment LIMIT 1`, the mysql CLI's first statement, was `ERROR 1149 syntax error at or near "@@"`, and no MySQL client could be benchmarked). `serve_protocol_statement` is the one place for them, ahead of the session and ahead of the engine's form of the text (below — `SET NAMES utf8mb4 COLLATE utf8mb4_0900_ai_ci` is answered, never refused for its collation; a `?` makes no protocol statement in a `COM_QUERY` text, which then gets MySQL's syntax error): `classify_protocol_statement` reads the text with MySQL's lexical rules (`protocol/lexer.hpp`, `tokenize`: below) and recognises, by grammar and never by substring, exactly: a SELECT list made of system variables (`@@[global. | session. | local.]name`) and the session functions `DATABASE()` / `SCHEMA()`, `VERSION()`, `USER()`, `CURRENT_USER`, `CONNECTION_ID()`, each with an optional alias, an optional `LIMIT`, nothing else (the shape the mysql CLI, Connector/J's `loadServerVariables`, the Go driver's `SELECT @@max_allowed_packet`, mysql-connector-python's `SELECT @@session.autocommit` / `@@session.sql_mode` send); `SHOW [GLOBAL | SESSION] VARIABLES [LIKE '…']`; `SHOW WARNINGS [LIMIT …]`; `SET NAMES` / `SET CHARACTER SET`; and a SET whose every target is a system variable (`SET @@session.x = v`, `SET GLOBAL x = v`, `SET a = 1, b = 2`, `SET [SESSION] TRANSACTION …`), which goes to the session's `execute_setting` (above). Anything else — `SELECT @@version + 1`, a FROM, a user variable `@x`, a second statement — goes to the session as it is. The answers (`answer_protocol_statement`) are what the server actually does, in agreement with the handshake: `@@version` is `SERVER_VERSION`; the handshake and every text column definition announce `utf8mb4_bin` (46, `SERVER_COLLATION_ID`, `protocol_const.hpp`: the engine compares strings byte by byte — `std::string_view` comparison in its `apply_operator.cpp` — so `'a' = 'A'` is false, MySQL's binary collation; the old `utf8mb4_general_ci` handshake and `utf8_general_ci` (33) columns promised a case-insensitive comparison nothing makes) and `@@character_set_client` / `_connection` / `_server` / `_database` are `utf8mb4`, the collations `utf8mb4_bin`, `@@character_set_results` NULL (results are sent as stored, never converted — what Connector/J would otherwise SET); `@@autocommit` 1 and `@@transaction_read_only` 0 (a SET changes nothing); `@@transaction_isolation` / `@@tx_isolation` `REPEATABLE-READ` (a transaction reads the snapshot taken when it began); `@@wait_timeout` / `@@interactive_timeout` the connection's read timeout; `@@max_allowed_packet` the largest command the server reads (`MAX_ALLOWED_PACKET`: one packet, as no command split over several is reassembled); `@@lower_case_table_names` 1 (the engine folds unquoted names, and the frontend folds a backquoted one); `@@sql_mode` the one constant `PIPES_AS_CONCAT,STRICT_TRANS_TABLES` — how the frontend reads the text (below: neither `ANSI_QUOTES` nor `NO_BACKSLASH_ESCAPES`, the lexer reads no other mode), `||` concatenating as the engine does. A variable the server does not have is `ER_UNKNOWN_SYSTEM_VARIABLE` (1193), as MySQL 9 answers the ones it dropped (`@@query_cache_size`). `DATABASE()` is NULL: COM_INIT_DB and the HandshakeResponse's database are accepted without effect. SHOW VARIABLES lists them sorted by name, `LIKE` with `%`, `_` and a backslash escape, without case; SHOW WARNINGS is the empty list (every OK / EOF packet says 0 warnings). These answers do not touch the session, so they are given in any block, a failed one included — driver housekeeping is never what fails a block. A driver may prepare them too (`COM_STMT_PREPARE` of `SELECT @@x`, `SET @@x = ?`): `prepare_protocol_statement` answers `STMT_PREPARE_OK` with the answer's columns (computed at prepare, as MySQL resolves a system variable then — an unknown one is refused at prepare) and one parameter per `?`, keeps the statement in the frontend (`prepared_stmt_meta::protocol`, no session entry), and every `COM_STMT_EXECUTE` answers it as `COM_QUERY` does, in the binary protocol (`execute_protocol_statement`; a SET through the session's `execute_setting`, the bound values unread) — it never reaches the engine and never fails a block.

**The text is MySQL's, and the engine reads PostgreSQL's** (`protocol/lexer.hpp`, `to_engine_text`). Every `COM_QUERY` and `COM_STMT_PREPARE` text is read by MySQL's default lexical rules (neither `ANSI_QUOTES` nor `NO_BACKSLASH_ESCAPES`, the only rules the lexer knows) and written out in the engine's form before the session sees it: a string literal (`'…'` or `"…"`) becomes a standard SQL literal — MySQL's escapes read (`\0 \' \" \b \n \r \t \Z \\`, `\%` / `\_` kept with their backslash for LIKE, any other `\x` as `x`), a doubled quote one, adjacent literals joined, a quote written doubled; the other literal forms become such a literal too — `N'…'` and an introducer of a utf-8 character set (`_utf8mb4` / `_utf8mb3` / `_utf8` / `_ascii`, blanks allowed before the literal) text, `_binary'…'` (PyMySQL's bytes parameter), `X'…'` / `0x…` and `B'…'` / `0b…` bytes, which are written as a string when they are utf-8 text and refused `ER_NOT_SUPPORTED_YET` otherwise (the engine has no byte-string literal: its scanner's `X'…'` / `B'…'` are bit strings its transformer refuses, a cast to BLOB is "not supported yet", and `0x41` it read as `0 AS x41`), an introducer of any other character set `ER_NOT_SUPPORTED_YET`; `COLLATE <binary collation>` (`utf8mb4_bin`, `utf8mb4_0900_bin`, `utf8mb3_bin`, `utf8_bin`, `binary`) is dropped — it is the engine's own byte comparison — and any other collation refused `ER_NOT_SUPPORTED_YET`; a backquoted identifier becomes `"…"` folded to lower case; every comment (`#`, `-- `, non-nesting `/* */`) one blank, while an executable comment `/*!` / `/*!NNNNN` (NNNNN ≤ `SERVER_VERSION_ID`) keeps its content as code; `--` that is no comment is written `- -`. A text the engine would misread is refused: an unterminated literal, identifier or comment and a name beginning with `$` (`$1` is a parameter, `$tag$` a dollar quote for the engine) are `ER_PARSE_ERROR`, a NUL character `ER_NOT_SUPPORTED_YET` (the engine reads its text up to the first NUL); like an engine parse error, the refusal fails an open block (`refuse_text`); a text of comments only is `ER_EMPTY_QUERY`. **The status flags never carry `SERVER_STATUS_NO_BACKSLASH_ESCAPES`**, as MySQL's defaults do not: PyMySQL, libmysqlclient (`mysql_real_escape_string`), mysql-connector-python, Connector/J and the Go driver then escape a string value with a backslash — PyMySQL does so for the values of a tuple / list parameter whatever the flag says — and the frontend reads exactly that. (The old flag told drivers to double quotes while the text went to the engine untouched: PyMySQL's nested values still came with `\'`, which the engine's standard strings took as a backslash and the end of the literal — `WHERE name IN %s` with `["x') OR 1=1 --"]` ran the injected `OR`.) The binary protocol's bound values never pass through the text and are untouched. `tests/mysql-front/test_protocol_statement.cpp` pins the lexer, the engine's form of the text (literals, identifiers, comments, placeholders, refusals), the classification over the drivers' exact texts and the answers down to the packets; `tests/system/test_frontend_mysql_protocol.cpp` the same over a raw socket (the handshake's collation and flags, literals round-tripping, the escaped-quote injection, `#`, a `?` in `COM_QUERY`, prepared protocol statements); `tests/test_mysql_client_housekeeping.py` PyMySQL and mysql-connector-python on the live server (the tuple-parameter injection among them).

**A MySQL `?` never reaches the engine.** `COM_STMT_PREPARE` writes every `?` placeholder as the engine's `$n` (`to_engine_text`, above: a `?` inside a literal, a quoted identifier or a comment is text; blanks keep `$n` apart from a name or number it is glued to — `THEN?` is `THEN $1`, never the name `THEN$1`) before the session sees the text, and keeps that text for every re-prepare; a prepare whose engine parameter count is not the number of `?` written is refused (`ER_NOT_SUPPORTED_YET`) rather than binding values to other parameters. In a `COM_QUERY` text a `?` outside a literal or comment is `ER_PARSE_ERROR`, as MySQL answers it. The engine's grammar reads a bare `?` as an operator: `SELECT ? + 1 FROM t` reached the engine's `transform_jsonb_exists` and killed the process (OTB-null-operand, `docs/proposals/otterbrix-embedding.md` §4.19) — once through the old first prepare of the raw text, and through `COM_QUERY`, which passed its text on untouched. `SELECT ? FROM t` prepares, and its execution throws `std::bad_variant_access` inside the engine's executor (`validate_schema_impl` over a parameter node): the session's future breaks, and the client gets `ER_UNKNOWN_ERROR` with the bridge's message rather than the errno text under a syntax-error code (`answer_await_failure`, below).

**A payload's column count is what tells a resultset from an affected count.** Both connections send an OK packet / a `CommandComplete` without `RowDescription` for a payload with no columns (`column_count() == 0`, the count being `reported_rows()` = the engine's `affected_rows`) and a resultset otherwise; they never consult the statement kind. The invariant that makes this sound — a row-producing statement (SELECT, set operations, DML with RETURNING) never reaches a frontend as a column-less payload — is enforced upstream in `otterstax::engine::execute_statement` (`schema_error`, `otterbrix/operators/engine_requests.hpp`), so a SELECT the engine could not type is an error on the wire, not a `SELECT 0` / OK. `tests/test_pg_extended_protocol.py` and `tests/test_mysql_wire_protocol.py` pin it with `SELECT big FROM <hugeint table>`. The MySQL OK packet (`build_ok`, `mysql_server/packet/packet_utils.cpp`) carries `affected_rows` and `last_insert_id` as length-encoded integers — a single byte holds a count only up to 250, and 0xFB..0xFF in that position are the NULL / int-size markers (`tests/mysql-front/test_reader_writer.cpp`, "build_ok: affected rows are a length-encoded integer"; `test_remote_dml_row_counts_span_chunks` in `tests/test_mysql_client_mysql_backend.py` drives a 1000-row count over the wire).

**A result column the wire cannot encode is a protocol error, never a dropped connection.** `frontend::{mysql,postgres}::get_field_type` (`frontend/common/utils.cpp`) answers `std::optional<field_type>` — nullopt for a logical type the protocol has no type for (UHUGEINT, DATE, TIMESTAMP, UNKNOWN, …). `find_unsupported_column<frontend_type>` (`resultset_utils.hpp`) names the first column that `is_encodable` rejects under the requested result formats (Bind convention: none = text, one for all, one per column): the type must be mapped AND the encoder of that format must have a case for it — the binary encoder carries scalars only, so ENUM/STRUCT/ARRAY/LIST pass in text and are refused in binary.

**DECIMAL and HUGEINT are carried, and their refusal is per format rather than per type.** Both map to MySQL `NEWDECIMAL` (0xF6) and PostgreSQL `NUMERIC` (oid 1700) — neither wire has a 128-bit integer type, and the fixed-point type each one does have carries its value as a string of digits, so every value of the range arrives intact where a 64-bit type would have to round or refuse. A HUGEINT is `decimal_to_text` at scale 0: the stored 128-bit integer, all of its digits and nothing after the point. It has no `(width, scale)` extension and **no sentinels** — the extremes of its range are ordinary values a `hugeint` column may hold, so unlike a DECIMAL none of them is reinterpreted as `NaN`/`±Infinity`; its magnitude is taken in unsigned arithmetic, so the most negative int128 (which has no positive counterpart) renders exactly instead of overflowing. On the MySQL wire the column definition reports `decimals` 0 and a length of 40 (39 digits plus the sign). `uhugeint` is mapped by neither wire and keeps taking the refusal path. For a DECIMAL, `decimal_to_text` (`resultset_utils.cpp`) renders a cell by putting the point back into the stored unscaled integer where the scale of the type says it belongs — DECIMAL(18, 4) holding 12345 is `1.2345`, never `12345`, which is the same corruption the Arrow path removed. The integer is read at the width its precision needs (INT16 / INT32 / INT64 / INT128, `decimal_storage_for_width`) and sign-extended; the engine's non-finite sentinels (the extremes of that integer's range) come out as PostgreSQL spells them for NUMERIC — `NaN`, `Infinity`, `-Infinity` — never as the finite number the sentinel would otherwise read as. MySQL takes that rendering in **both** formats, because a NEWDECIMAL field of a binary resultset row is a length-encoded string exactly as in a text row (this is how boost.mysql reads it back: `deserialize_binary_field_string`). PostgreSQL takes it in **text only**: binary NUMERIC is a sequence of base-10000 digit groups behind a weight/sign/dscale header, which PostgreSQL documents as backend-internal rather than as part of the client protocol ("Values passed in binary format require knowledge of the internal representation expected by the backend" — libpq, `PQexecParams`), and a PG `DataRow` states each field's length before its bytes, so a guessed encoding would desynchronise the row rather than merely mis-state a number. `is_encodable<POSTGRES>(DECIMAL, BINARY)` is therefore false and the column is refused with the usual `ErrorResponse 0A000` naming the column, its type and the format, while `is_encodable<MYSQL>` accepts it in both. On the MySQL wire the column definition also answers for itself: `apply_decimal_metadata` (`resultset/column_definition_41.cpp`) sets `decimals` to the scale and the length to the digits plus sign and point, on `COM_QUERY`/`COM_STMT_EXECUTE` results and on the `COM_STMT_PREPARE` schema alike. On the PG wire the field's `type_modifier` stays -1 — what PostgreSQL itself sends for a numeric with no declared typmod — and the scale rides in the value's own trailing digits, as PG's text output does. Every connection runs it before building a resultset or a RowDescription: PG `handle_query` (text), `do_describe` (statement: text, portal: the Bind formats), `handle_execute` (the portal formats, on every Execute); MySQL `handle_query` (text), `handle_prepared_stmt` (the schema, binary — `COM_STMT_EXECUTE` is binary), `handle_execute_stmt` (the executed chunk, binary). The refusal is `ErrorResponse 0A000` (`FEATURE_NOT_SUPPORTED`) / `ERR 1235` (`ER_NOT_SUPPORTED_YET`, SQLSTATE 42000) with `unsupported_column_message` — `column 'big' has type HUGEINT (15), which the PostgreSQL wire cannot encode in text format` — and the connection stays usable. The encoders' `default:` branches are unreachable after that check and `assert` it; nothing in the frontends throws. `tests/mysql-front/test_wire_type_support.cpp` pins the mapping and the check.

**A NULL is a property of the cell, not of the column's type, and a binary resultset row carries it in the row's NULL bitmap alone.** `mysql_resultset::encode_row_binary` asks `chunk.data[i].is_null(row)` per cell — which also answers true for every row of a column whose type is NA, so that case needs no separate test. The bitmap is `(column_count + 7 + 2) / 8` bytes and the bit of column *i* sits at *i + 2*, because a ResultsetRow reserves the first two bit positions; this is exactly how boost.mysql — the client this server answers — reads it back (`binary_row_null_bitmap_offset = 2`, `null_bitmap_parser::byte_count`), and for a field whose bit is set it consumes **no bytes**. So a NULL cell sets its bit and writes nothing. Deciding the bitmap from the column's *type* instead (`type() == NA`) left the bit clear for every empty cell of a typed column and still wrote the untouched slot's bytes: the client could not tell `NULL` from `0`, and because those bytes stayed in the row every field after them was read at the wrong offset — a string's length prefix taken out of a stale integer. Text rows state a NULL per cell already (the `0xFB` marker). On the PostgreSQL side a `DataRow` writes the `-1` length and no bytes, and the length a **binary** field states in front of its bytes is computed where it is written (`postgres_resultset::add_row`) rather than from a list built in a parallel pass — such a list holds no entry for a NULL cell, so every binary field after one took the previous column's length and desynchronised the row. `estimate_{text,binary}_field_size` answer for an empty cell without reading its slot. `tests/mysql-front/test_resultset.cpp` pins the bitmap bytes (a NULL in the first and the last column, a row of all NULLs, and columns 6–7 crossing into the second bitmap byte) and that no value bytes follow a set bit. **A result column without a name** (`SELECT 1`) has no alias in the prepared schema, and the engine's `complex_logical_type::alias()` has no null guard for such a type (`has_alias()` has one): PG `do_describe` (`Describe` of a statement or a portal) and MySQL `handle_prepared_stmt` (`COM_STMT_PREPARE`) name it with the empty string, which is the name an executed chunk carries for it and what the simple `Query` / `COM_QUERY` send. A bare `alias()` there dereferenced null on the pool thread and killed the process. The executed result can carry such a column as well — `SELECT 1 UNION ALL SELECT 2` (a set operation's column has no alias at all, where an executed `SELECT 1` has an empty one), and on rc-2 a `SELECT` over a VIEW — so the resultset builders `mysql_resultset::add_chunk_columns` / `postgres_resultset::add_chunk_columns` (behind `COM_QUERY`, `COM_STMT_EXECUTE`, the simple `Query` and the `Execute` of a portal nobody described) name it with the empty string too. Every `alias()` in the frontends sits behind `has_alias()` (the tsl converters refuse an unnamed chunk column instead). `tests/system/test_frontend_malformed_packet.cpp` pins all of them.

**PostgreSQL extended query specifics.** `Describe(statement)` answers `ParameterDescription` followed by `RowDescription` (text formats) or `NoData`. **A statement that answers rows is described, never `NoData`**: `NoData` states that the statement will not return rows, and the clients that live by the statement's description (Npgsql prepared, asyncpg, tokio-postgres, lib/pq, PgJDBC in its describe path) take it at its word. What the prepare knows goes out — for a parameterized statement that is the plan's own projection, the columns named and untyped (`query_session_t::prepare_schema`, `session/CLAUDE.md`), so they are described as `text`. **`Describe(portal)` describes the portal by running it**: a portal is a BOUND statement, so a row-producing one — decided by the statement kind (`prepared_stmt_meta::tag`), never by the columns of a result nobody has yet — is executed and described from the chunk it actually answers, with the portal's own result format codes, which belong to the `Bind` that created the portal (`portal_meta::format`). The result stays in the portal, so the `Execute` behind it streams that result instead of running anything again: the description is exact and costs no extra round-trip. A DML portal is NOT run — describing one would write, and write twice for a client that binds it again — so it is described from the prepared schema: a `RETURNING` list is described by the columns it projects, resolved at prepare from a `LIMIT 0` probe of the target relation (the session's RETURNING describe), and a statement that answers an affected count alone is `NoData`. The `Execute` is what writes, in both cases. **An `Execute` whose result is not the shape the client was given refuses instead of streaming it**: when the statement was described before Bind and the portal was not described since, the executed chunk is checked against that description column by column (`same_wire_shape`, `resultset/postgres_resultset.cpp`: the same count and the same type oid per column; names are not compared, since a `DataRow` is decoded by position and type and an executed column may legitimately carry a name the prepared schema had none for). A divergence is `ErrorResponse 0A000` carrying PostgreSQL's own wording, `cached plan must not change result type` (`plancache.c`, `RevalidateCachedQuery`). A parameterized statement's pre-Bind description carries no types, so this is what a client that decodes by it gets — a clear error — rather than one type's bytes read as another's. An `Execute` with a row limit sends that many rows and `PortalSuspended`; the portal keeps the result and the next `Execute` on it continues from where it stopped, `CommandComplete` counting the rows of that `Execute`. Text-format `Bind` parameters are converted by `parse_text_parameter` (`std::from_chars`, no exceptions); a bad literal ends the `Bind` with an `ErrorResponse` and no `BindComplete`. **Errors and `Sync`** follow the protocol's pipeline rule, kept in `pipeline_state` (`connection/pipeline_state.{hpp,cpp}`): every extended-query message (`Parse`, `Bind`, `Describe`, `Execute`, `Close`, `Flush`) begins or continues a pipeline; a non-fatal error inside it (`send_error_response`, whatever the handler) sends the `ErrorResponse` alone, `handle_packet` discards every following message until the `Sync` (`Terminate` still ends the connection), and that `Sync` sends the single `ReadyForQuery`. A simple `Query` is outside any pipeline — it ends one, since it answers `ReadyForQuery` itself — so its error keeps `ErrorResponse` followed by `ReadyForQuery` at once. **The `ReadyForQuery` status byte is the transaction block's, never the pipeline's**, as in PostgreSQL, and it is the session's block on every route ("Transactions" above): `I` outside a block — an error there fails nothing, so a failed pipeline's `Sync` answers `I` — `T` inside one, `E` once an error inside the block failed it, until `ROLLBACK` or `COMMIT` ends it (`COMMIT` of a failed block answers `CommandComplete ROLLBACK` and `I`). Statements sent inside a failed block are refused with `25P02` by the engine (and by the session for what does not run on the engine). `tests/mysql-front/test_pg_frontend_packets.cpp` pins `pipeline_state`, `tests/system/test_frontend_transactions.cpp` and `tests/system/test_frontend_malformed_packet.cpp` the status over the wire, `tests/test_pg_extended_protocol.py` the live server (`read_failed_pipeline` asserts exactly one `ReadyForQuery` and nothing after it).

Packet encoding/decoding lives in `{mysql,postgres}_server/packet/` and `{mysql,postgres}_server/{mysql,postgres}_defs/`. Result-set serialisation is in `{mysql,postgres}_server/resultset/`.

**The secrets a connection is handed come from a CSPRNG.** The MySQL handshake's scramble (`mysql_scramble`, made a legal string as MySQL's `generate_user_salt` makes it: 7 bits, never NUL or `$`) and the PostgreSQL BackendKeyData secret — what a CancelRequest presents — are `frontend::secure_random_bytes` (OpenSSL `RAND_bytes`, thread-safe). They used to come from one `std::mt19937` shared by every connection thread: a data race between concurrent handshakes (TSAN) and a sequence a client could reconstruct from the scrambles it was sent and so predict other connections' cancel keys. When no secure bytes can be had the connection is refused (MySQL an ERR packet in place of the handshake, PG `FATAL XX000`).

**A client packet shorter than its fields is a protocol error, never an exception.** `packet_reader_base` (`common/packet_reader_base.{hpp,cpp}`, the MySQL little-endian and PG big-endian readers derive from it) reports a read past the end of the packet through a sticky fault state — `ok()` / `fault()`, `packet_fault::underflow` for too few bytes (a NUL-terminated string without its terminator included), `packet_fault::invalid_marker` for a MySQL length-encoded integer starting with 0xFB/0xFF. A failed read moves the position by nothing, its returned value is not data, and every later read fails too, so a handler checks once after a group of reads and before acting on any value. The byte-merging helpers in `common/utils.hpp` index unchecked (`operator[]`) — their callers own the bounds (`check_bounds`, or a header read to its exact size). Every handler that decodes a packet checks the reader: MySQL `handle_auth`, `COM_STMT_EXECUTE` / `COM_STMT_CLOSE` in `handle_command`, `handle_execute_params` (after the types, after the values); PG `read_initial_message` (the protocol version), `handle_startup_message`, the `Query` / `Parse` / `Bind` / `Execute` / `Close` / `Describe` cases of `handle_packet`, `handle_parse`, `handle_bind`. On MySQL the answer is `send_malformed_packet_error` — `ERR 1835` (`ER_MALFORMED_PACKET`) then `finish()`. On PG it follows PostgreSQL: after startup a malformed message — a `remaining()` pre-check (`Truncated PARSE message ...`) or the reader's fault — is `ErrorResponse 08P01` (`PROTOCOL_VIOLATION`) with severity **ERROR**, and the connection stays usable; the error obeys the pipeline rule above (inside an extended-query pipeline the `ErrorResponse` goes alone, the messages up to the `Sync` are discarded and the `Sync` answers the one `ReadyForQuery` with the transaction status, `I` outside a block; a simple `Query` without its terminator gets `ErrorResponse` + `ReadyForQuery` at once). The next message is framed correctly because every PG message is length-prefixed and `read_packet_payload` reads exactly the declared length before `handle_packet` runs — a short body is a defect of that message alone.

**A body longer than its fields is the same `ERROR 08P01`**, message `invalid message format` (PostgreSQL's `pq_getmsgend`), and it follows the same pipeline rule. `Query`, `Parse` (`handle_parse`), `Bind` (`handle_bind`), `Execute`, `Describe` and `Close` check `remaining() == 0` after their last field, before acting on the message. `Sync` and `Flush` must have an empty body: `Sync` ends the pipeline first, so its error gets `ReadyForQuery` at once, while `Flush` is an extended-query message, so its error waits for the `Sync`. As in PostgreSQL, `Terminate` ends the connection whatever its body holds, and `CopyData` / `CopyDone` / `CopyFail` outside COPY are accepted and ignored.

**A message type the protocol does not define is `FATAL 08P01`** `invalid frontend message type <n>` (the byte in decimal), followed by the close. This covers `FunctionCall` (`F`), which the frontend does not implement, and a `PasswordMessage` after startup. `validate_payload_size` decides it from the header, before waiting for the body the length announces, since the message boundaries are presumed lost. The other FATAL errors are a malformed `StartupMessage` (no session yet: an unterminated parameter, no room for the protocol version) and the transport (`IO_ERROR`) and resource (`INSUFFICIENT_RESOURCES`) failures; each closes the connection. `tests/mysql-front/test_reader_writer.cpp` and `test_pg_frontend_packets.cpp` pin every primitive on a truncated buffer; `tests/system/test_frontend_malformed_packet.cpp` sends the truncated packets over raw sockets (`tests/system/raw_wire_client.hpp`) and asserts the error packet, the MySQL close / the PG `ReadyForQuery` followed by a served `SELECT 1` on the same connection, and that the server keeps serving; `tests/test_pg_extended_protocol.py` (`test_malformed_message_is_a_protocol_error_not_a_disconnect`) pins the PG contract on the live server.

## Spark Connect (`spark_connect_server/`)

**One query session per Spark session.** The service keeps the Spark sessions in an `idle_session_registry_t` (`spark_sessions.hpp`; Spark `session_id` → `session_ptr`, the registry its only owner): no RPC holds a session; every step of an RPC calls the registry itself (`spark_sessions_`, the time `std::chrono::steady_clock::now()` at the call; there is no wrapper of the service's own): `open_or_use(id, now, step, open)` for the first step of an ExecutePlan / AnalyzePlan, `use(id, now, step)` for a step that never opens one (`fail_unanswered`) — under the registry's lock the step only queues its statement (`actor_zeta::send`), and the answer is awaited outside the lock. A step whose answer the RPC awaits goes through `begin` (`idle_session_registry_t::begin`), which counts it in work in the session's entry (`steps_in_work`, under the same lock) until `finish` (which also restarts the idle clock) — called by a `boost::scope::scope_exit` however the wait ends (answered, timed out, broken, the coroutine unwound): the statement step of ExecutePlan and of AnalyzePlan until the request ends, `fail_refused`'s report, AnalyzePlan's `close_statement` and every catalog read until its answer came (`handle_catalog_relation` takes the registry and the Spark session id). A session with a step in work is never closed as idle. The first step of an ExecutePlan / AnalyzePlan opens the session on the Spark session's first RPC (`open_or_use`, refused for a closed id); `ReleaseSession` (`idle_session_registry_t::release`) erases it under the lock, which closes the query session, and remembers its id like an expired one's (below): a request that comes back with it is refused `[INVALID_HANDLE.SESSION_CLOSED]`, as Spark's SessionManager tombstones a closed session. A statement the session already took runs to its end and its answer goes out; a later step of a request the close cut short — or its statement, queued behind another and answered `connection_closed` — is refused `[INVALID_HANDLE.SESSION_CLOSED]` (`error_status`). `stop()` closes every Spark session once no RPC runs (`idle_session_registry_t::clear`), with the other servers' connections. A local transaction therefore spans the `spark.sql()` statements of one Spark session. **Expiry, as Spark Connect's SessionManager does it:** a session with no step in work whose last RPC step (or the end of its last awaited step) was longer ago than `service.spark_connect.session_timeout_s` (default 3600 — Spark's `spark.connect.session.manager.defaultSessionTimeout` is 60m; 0 keeps sessions until ReleaseSession) is closed by the maintenance thread (every 30 s, `kMaintenanceInterval`, Spark's `maintenanceInterval`) — a statement it is running goes on to its end; closing its query session rolls back a transaction it left open (`session/CLAUDE.md`, the close protocol). Its id is remembered (the last 1000, Spark's `closedSessionsTombstonesSize`): an RPC that comes back with it is refused `FAILED_PRECONDITION` `[INVALID_HANDLE.SESSION_CLOSED]` rather than handed a fresh session that would know nothing of its transaction. A statement the await bridge gave up on — timed out, or broken (no answer came back) — fails an open block behind it (`fail_unanswered`, by the await's status, as the MySQL and PostgreSQL frontends do). A request ExecutePlan refuses before the session runs it — a `spark.sql()` text `classify_sql` cannot parse, `spark.sql()` over DataFrame arguments, a plan it does not translate — fails an open block like any other error (`fail_refused`: `query_session_t::fail_transaction`, awaited before the refusal goes out, so the next statement finds the block failed); outside a block it fails nothing.

`SparkConnectServiceImpl` (`service.{hpp,cpp}`) is an asio-grpc server (Boost backend) over the Spark Connect protos vendored from apache/spark v4.2.0 (`proto/spark/connect/`, gRPC stubs generated for `base.proto` only). `start()` runs one `agrpc::GrpcContext` per thread of `service.runtime.spark_connect_io` (`SparkConnectServerConfig::io_threads`), each on its own thread, and records the port gRPC bound (`local_port()`; tests bind port 0), with every RPC handler registered on each; a failed `BuildAndStart` (the port taken) is logged and leaves the other frontends running. `spark_connect_server` wraps it for `main.cpp`, which starts it after the PostgreSQL server and stops it with the others; the listen address is `service.spark_connect` (`config/CLAUDE.md`). Every handler is a coroutine on its context's `agrpc::GrpcExecutor` whose Tracy zone never spans a `co_await`. Logger tag `SparkConnectServer`. Each ExecutePlan / AnalyzePlan request runs on its Spark session's query session under a fresh statement id (above).

- **ExecutePlan** (`service_execute_plan.cpp`) — a `SqlCommand` (`spark.sql()`: the text is `SqlCommand.sql` from 3.5 clients, `SqlCommand.input.sql` from 4.x) is answered the way Spark's own server answers it, and `classify_sql` tells which way by parsing the text (`GreenplumParser::parse`; nothing runs, no actor is asked). A SELECT of the core grammar (`T_SelectStmt`, no grammar extension) answers `sql_command_result.relation` — its SQL relation, unrun (`sql_command_relation`) — so the query runs once, when the client acts on the DataFrame. Any other statement (DDL, DML, CREATE EXTERNAL TABLE / COPY, Kafka DDL, `INSERT INTO kafka.*`) runs once through `query_session_t::execute` and answers an empty `LocalRelation`, which the client never sends back to be run; the statement's own output rows (a RETURNING list) are dropped. A text that does not parse, and `spark.sql()` over DataFrame arguments, are `INVALID_ARGUMENT`. A root relation is answered by kind: `Relation.catalog` (`spark.catalog.*`) through `handle_catalog_relation`; the empty `LocalRelation` as an empty result; a SQL relation without arguments (`is_bare_sql`) through `query_session_t::execute`, so it takes the whole SQL path; a `ShowString` by rendering its input's rows (below); anything else — a DataFrame, a SQL relation with arguments or under operations included — is translated by `plan_translator/relation_to_plan` into a `ParsedQueryData` and goes to `query_session_t::execute_plan`. A plan carrying a window expression is refused before any of that, any other command by name (`Spark command <name> is not supported`). The result streams as one Arrow IPC `ArrowBatch` per result chunk — the schema and the operation id on the first, empty chunks included — followed by `ResultComplete`. Every response carries a `response_id`, a random version-4 UUID (`frontend::secure_uuid_v4`, the `00112233-4455-6677-8899-aabbccddeeff` form `base.proto` asks for); it used to be an `mt19937_64` seeded per call with 32 bits of `random_device` — ids repeated after ~65k responses — and when no secure bytes can be had the stream ends `UNAVAILABLE` instead. A translation refusal is `INVALID_ARGUMENT`, an execution or encoding failure `INTERNAL`.
- **AnalyzePlan** (`service_analyze_plan.cpp`) — `schema` (`df.schema`) is a prepare, never an execution: SQL — a `SqlCommand` or a SQL relation without arguments — through `query_session_t::prepare_schema`, a DataFrame through `query_session_t::prepare_plan`, then `query_session_t::close_statement` for the entry the prepare left on the session (a failed close is logged; the schema is still answered); the empty `LocalRelation` is an empty struct and prepares nothing. A row-producing statement whose prepared schema is not a STRUCT is refused (`INTERNAL`) rather than described from anything else; a statement without rows is an empty struct. `spark_version` answers `4.2.0`, `explain` the text `EXPLAIN not supported`, `is_local` / `is_streaming` false, `input_files` nothing, every other variant a placeholder.
- **DataFrame translation** (`plan_translator/relation_to_plan.cpp`, `expression_to_plan.cpp`) — each operation is stacked as a clause of the current aggregate where the engine's fixed clause order (match → group → having → sort → select → distinct → limit) runs it at the point Spark does (`can_stack`): consecutive filters are ANDed into one match, and a limit or offset on a window merges into one exact window (`merged_window`). Any other operation makes the aggregate a derived table (`derive`: the FROM of a fresh aggregate, the transformer's `FROM (subquery)` shape); a remote read stays the inner aggregate with its clauses — the query block the federation pushes down whole. A Read names its table as the SQL path reads it: one to four parts, three read as database.schema.table (the federation takes the database slot of `alias.db.table` for the alias), four keeping the alias slot. A SQL leaf is parsed by `GreenplumParser::parse_fragment` (a single SELECT, no sub-queries) into the plan's shared parameter node. Refused (`unimplemented_yet`): an outer operation that reads a column an inner `select()` renamed (the validator resolves such a name by its source column), `unionByName()`, and an aggregate whose arguments are all constants other than `count(<non-null literal>)`, which is translated as `count(*)` — the engine folds an all-constant argument once per chunk (root `CLAUDE.md`, Known Constraints). An `avg` averages its argument cast to DOUBLE, in the shape the SQL transformer gives `avg(CAST(col AS double))`, as Spark's `Average` does: the engine's `avg` answers DOUBLE for an integer argument (fraction kept) but keeps a FLOAT argument's FLOAT and a DECIMAL's DECIMAL. The user-facing list is `docs/spark_connect_unsupported.md`.
- **`df.show()`** (`show_string.{hpp,cpp}`) — a `ShowString` is answered with one row of one STRING column, `show_string`: the input's rows rendered the way Spark 4.2's `Dataset.showString` renders them (its cell spelling, `NULL`, truncation to `truncate` characters with `...`, right-aligned when truncating, the vertical `-RECORD` form, the `only showing top N rows` footer without a trailing newline, as in 4.x). A bare SQL input runs through `query_session_t::execute` (every row; the first `num_rows` are shown); any other input is fetched under a limit of `num_rows + 1` through `execute_plan` (`show_string_input_plan`: the extra row decides the footer). A cell of a type it cannot render (LIST, STRUCT, MAP, BLOB, UUID, INTERVAL, …) is a `conversion_failure` naming the column.
- **The other RPCs** (`service_misc.cpp`) — Config answers the four runtime keys clients read at session start and an empty value for any other key (`set` / `unset` are accepted, nothing is kept); ReleaseSession closes the Spark session (above); Interrupt, ReleaseExecute, ArtifactStatus, AddArtifacts and FetchErrorDetails are acknowledged and do nothing; ReattachExecute answers `NOT_FOUND` `INVALID_HANDLE.OPERATION_NOT_FOUND`, since responses are not buffered. CloneSession and GetStatus (4.1+) are not implemented.
- **Awaiting the session** — `await_future.hpp` is the gRPC form of `common/asio_future_bridge.hpp`: a `GrpcContext` drives only its completion queue and a handler cannot await the bridge's `any_io_executor` coroutine, so it polls `take_ready()` between `agrpc::Alarm` waits (16 µs, doubling to a 1 ms cap). The contract is the bridge's: an `otterstax::awaited_t` — the session's result, or the bridge's own failure told by its status (`timed_out` at `DEFAULT_TIMEOUT`, `broken` when the channel closed), never by a code — the message on the caller's resource.
- **`spark.catalog`** (`catalog_relations.{hpp,cpp}`; the pure half, no actor and no I/O, in `catalog_rows.hpp`) — answered from the engine's own catalog: `SELECT oid, relname, relnamespace, relkind FROM pg_catalog.pg_class`, then `SELECT oid, nspname FROM pg_catalog.pg_namespace`, then `SELECT uid, database_name, schema_name, table_name, remote_database FROM federation.remote_tables`, through `query_session_t::execute`; a table's columns from `query_session_t::prepare_schema` of `SELECT * FROM <every part double-quoted>` (described by the engine; a remote table's from `federation.remote_columns`), then `close_statement`. Catalog `otterstax`, current database `default`. The databases are the user namespaces (oid ≥ 16384) plus `default`, which holds the tables created unqualified, plus every connection alias that has remote tables. A remote table's Spark namespace is `[alias, db]` for MySQL / ClickHouse, `[alias, db, schema]` for PostgreSQL; a local table's is `[d]` — so `".".join(namespace + [name])` is the name the SQL path resolves. Kinds r / g are `MANAGED`, v / m `VIEW`, a remote table `MANAGED`; system rows and namespaces, the other kinds, the `federation` database and its tables and the Kafka bookkeeping tables (`kafka.__sources`, `kafka.<source>__offsets`) are hidden. Supported: `currentCatalog`, `listCatalogs`, `currentDatabase`, `listDatabases`, `getDatabase`, `databaseExists`, `listTables`, `getTable`, `tableExists`, `listColumns`; any other operation is `unimplemented_yet` `spark.catalog.<op> is not supported`. Every answer is laid out by position, as PySpark 3.5–4.2 reads it.
- **Result encoding** (`result_encoder.cpp`, `plan_translator/type_converter.cpp`) — a column the otterbrix Arrow converters cannot carry (MAP, NA, BLOB, HUGEINT / UHUGEINT, UUID, ENUM, …) is refused as `conversion_failure` naming the column before either converter runs (both throw on such a type); an unsigned column is re-tagged as the signed type of the same width (Spark has no unsigned types; `COUNT` is UBIGINT), and an unnamed one is `col<i>` — in the batch and in the reported schema alike.

What a PySpark user can and cannot do is in `docs/spark_connect_unsupported.md`. Tests: `tests/unit/spark_connect/` (`test_unit_spark_connect`), `tests/system/test_spark_plan_execution.cpp` (`[spark-plan]`), `tests/system/test_prepare_plan.cpp`, `tests/system/test_spark_transactions.cpp` (a gRPC client against the server on port 0: a `classify_sql` refusal inside a block fails it, a released session id is refused), and the PySpark client matrix (`tests/CLAUDE.md`).
